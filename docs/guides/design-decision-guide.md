# 설계 판단 가이드

새 기능의 클래스, 모듈과 비동기 실행 방식을 정할 때 사용하는 기준이다. 먼저
데이터 흐름과 상태 소유자를 정한 뒤 필요한 최소 공개 API를 작성한다.

## 설계 순서

1. 입력과 출력, 실제 사용자 흐름을 한 문장으로 적는다.
2. 외부 장치·프로세스와 Python 내부 객체의 경계를 표시한다.
3. 계속 변하는 상태마다 단일 소유자를 정한다.
4. 외부에 필요한 최소 읽기 메서드를 정하고, 복합 상태가 실제로 필요할 때만
   snapshot을 만든다.
5. blocking I/O와 CPU·GPU 연산이 event loop를 막는지 확인한다.
6. 가짜 장치로 검증해야 하는 경계만 Protocol로 만든다.
7. `bootstrap.py`에서 객체 생성·연결·시작 순서를 확인한다.
8. 구현하지 않을 범위를 명시하고 코딩을 시작한다.

## 함수와 클래스

다음 조건 중 하나가 있을 때 클래스를 사용한다.

- 연결, 최신 값, 목표 또는 model처럼 수명주기 동안 유지할 상태가 있다.
- `start()`·`stop()`으로 명확한 자원 수명주기를 가진다.
- 여러 메서드가 같은 불변 조건이나 외부 연결을 공유한다.

입력을 출력으로 바꾸는 단순 변환은 함수 또는 상태 없는 클래스로 둔다.
`SegmentDecoder.decode()`처럼 순수한 처리를 억지로 async 서비스로 만들지 않는다.

## 모듈 경계

- `core/`에는 Desk·Vision과 무관하게 둘 이상의 기능이 실제로 사용하는 실행
  기반만 둔다.
- 장치 프로토콜과 기능 정책은 `modules/<기능>/`에 둔다.
- MQTT transport는 payload 의미를 모르고, JSON 검증은 해당 기능의
  `messages.py`가 담당한다.
- FastAPI route는 요청 검증과 서비스 호출만 담당한다.
- 정책 클래스는 FastAPI, aiomqtt, OpenCV 같은 framework 타입을 공개 API로
  노출하지 않는다.
- 외부 인프라의 실행 설정은 `infra/`, Python 객체는 `src/smart_desk/`에 둔다.

새 공통 모듈은 두 곳 이상에서 같은 책임이 반복된 뒤 만든다. 단, MQTT·시리얼·
카메라처럼 장치 없는 테스트가 반드시 필요한 외부 경계는 구현체가 하나여도 작은
Protocol을 둘 수 있다.

## async 판단

| 작업 | 기본 방식 |
| --- | --- |
| MQTT·HTTP·시리얼처럼 대기 가능한 I/O | `async def` |
| 이미 메모리에 있는 bool·단순 값 조회 | 동기 property 또는 `def` |
| 여러 값을 같은 시점에 전달해야 하는 복합 상태 조회 | 필요한 경우에만 불변 snapshot |
| OpenCV RTSP `read()` 같은 blocking I/O | 전용 thread 또는 검증된 executor |
| YOLO·얼굴 모델 추론 | executor 또는 model에 맞는 별도 실행 경계 |
| 짧은 상태 계산·Pydantic 검증 | 동기 실행 |
| 장기 반복 작업 | `TaskManager`가 관리하는 이름 있는 task |

`async`는 동시 실행 가능성을 나타내는 장식이 아니다. 실제로 기다릴 작업이 없으면
동기 메서드로 둔다. lock을 잡은 동안 MQTT publish, 파일 I/O 또는 추론을
기다리지 않는다.

## 상태와 명령

- 내부 가변 필드는 상태 소유자만 수정한다.
- 연결 여부처럼 단순한 상태는 `is_connected()` 같은 동기 메서드로 제공한다.
- 높이·관측 시각·센서 상태처럼 여러 소비자가 같은 시점의 묶음을 실제로
  사용해야 할 때만 불변 snapshot을 반환한다.
- snapshot을 만들었다면 판단에 필요한 값과 관측 시각을 포함하되, 사용하지 않을
  진단 필드를 미리 추가하지 않는다.
- 오래된 retained MQTT 메시지나 프레임을 현재 상태로 간주하지 않는다.
- 명령 이름과 수명주기 이름을 구분한다. 예를 들어 `stop()`은 리소스 종료,
  `stop_motion()`과 `send_stop()`은 책상 동작 정지다.
- STOP은 목표 변경, HOLD와 자동화보다 우선한다.

## singleton과 의존성

클래스 자체에 singleton metaclass나 전역 인스턴스를 넣지 않는다.
`bootstrap.py`가 객체를 한 번 만들고 `AppContainer`가 소유한다.

```text
FastAPI route / event handler → get_desk(), get_mqtt() 허용
DeskController 내부           → 생성자로 받은 monitor·relay 사용
```

핵심 클래스 내부에서 `get_container()`를 반복 호출하면 실제 의존성이 숨겨지고
테스트가 어려워진다. 반대로 작은 프로젝트에 DI framework를 추가하지 않는다.

## 선택 기준

| 질문 | 예 | 아니오 |
| --- | --- | --- |
| 상태와 수명주기가 있는가? | 작은 클래스 | 함수 |
| 외부 장치·프로세스 경계인가? | adapter와 필요한 Protocol | 직접 메서드 |
| 여러 값을 원자적으로 읽는 소비자가 있는가? | 최소 필드의 snapshot 검토 | property·단순 메서드 |
| 처리 지연 시 과거 데이터가 필요한가? | 크기가 제한된 queue 검토 | 최신 snapshot 교체 |
| 값이 배포마다 달라지는가? | Settings | 상수 |
| 물리적으로 넘을 수 없는 안전 한계인가? | 코드·펌웨어 상수 | 환경 설정 |
| Python이 반드시 프로세스를 소유해야 하는가? | lifecycle resource 검토 | Compose/system service |
| 같은 책임이 실제로 반복되는가? | 공통 helper 검토 | 기능 모듈에 유지 |

## 설계 완료 확인

- 상태 소유자가 하나인가?
- 외부에서 직접 수정할 수 있는 가변 필드가 없는가?
- 새 snapshot·wrapper가 실제 소비자의 요구를 해결하는가?
- 공개 메서드 이름만으로 동작과 수명주기를 구분할 수 있는가?
- 시작·종료·오류·재연결 경로가 있는가?
- STOP과 물리 상한을 우회하는 호출 경로가 없는가?
- fake로 핵심 정책을 검증할 수 있는가?
- 새 계층을 제거했을 때 더 단순하면서 같은 요구를 충족하지는 않는가?
- 현재 작업과 무관한 미래 기능을 미리 구현하지 않았는가?
