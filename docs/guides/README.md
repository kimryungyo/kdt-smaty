# 계획 및 설계 가이드

새 기능을 제안하거나 기존 작업을 더 세분화하기 전에 참고하는 공통 판단
기준이다. 현재 구조를 설명하는 아키텍처 문서와 달리, 이 폴더는 앞으로 무엇을
어느 정도까지 만들지를 결정하는 방법을 다룬다.

## 읽는 순서

| 문서 | 읽는 시점 | 핵심 질문 |
| --- | --- | --- |
| [프로젝트 원칙](project-principles.md) | 모든 계획을 시작할 때 | 이 프로젝트의 규모와 우선순위에 맞는가? |
| [설계 판단 가이드](design-decision-guide.md) | 클래스·모듈·인프라를 추가할 때 | 지금 이 구조가 실제로 필요한가? |
| [계획과 전달 가이드](planning-and-delivery-guide.md) | 작업 목록과 커밋을 나눌 때 | 구현·검증·완료 단위가 명확한가? |

## 적용 방법

- 이 문서들은 기본 선택을 빠르게 정하기 위한 기준이며 절대 규칙이 아니다.
- 예외가 필요하면 실제 요구사항, 안전 문제 또는 측정 결과를 근거로 남긴다.
- 책상 물리 안전, ESP32 보호와 기존 MQTT 계약은 단순화 원칙보다 우선한다.
- 현재 요구에 꼭 필요하지 않은 새 계층이나 상태 객체는 확정안처럼 추가하지 않는다.
  필요성이 애매하면 단순한 대안과 차이를 먼저 설명하고 사용자 확인을 받는다.
- 이미 확정된 구조는 [아키텍처 문서](../architecture/system-design.md)를 따르고,
  변경이 필요하면 코드 작업 전에 관련 문서를 함께 수정한다.
- 번호순 개발 작업은 [작업 목록](../tasks/README.md)에서 관리한다.

가이드가 구현보다 더 복잡해지지 않도록 새로운 규칙 문서는 반복되는 문제가
실제로 확인된 경우에만 추가한다.
