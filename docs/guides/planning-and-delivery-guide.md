# 계획과 전달 가이드

큰 roadmap을 실제 구현 가능한 작업으로 바꾸고, 테스트와 커밋까지 완료하는
기준이다. 계획의 목적은 문서의 양을 늘리는 것이 아니라 범위 이탈과 재작업을
줄이는 것이다.

## 작업 계획에 포함할 내용

새 작업 문서는 필요한 항목만 사용하되 최소한 다음 질문에 답해야 한다.

```text
목표: 완료 후 사용자가 할 수 있는 일은 무엇인가?
선행 조건: 어떤 코드·장치·결정이 먼저 필요한가?
범위: 이번 작업에서 실제로 변경할 것은 무엇인가?
제외 범위: 의도적으로 다음으로 미루는 것은 무엇인가?
인터페이스: 추가·변경되는 공개 메서드와 계약은 무엇인가?
안전: 실패·종료·단절 시 어떤 상태가 되어야 하는가?
검증: 단위·통합·실물 중 어떤 증거가 필요한가?
완료 조건: 무엇을 확인하면 작업을 끝냈다고 판단하는가?
```

`docs/tasks/`의 번호 문서는 며칠 단위의 상위 작업이다. 실제 구현을 시작할 때는
검토와 테스트가 가능한 0.5~2일 정도의 하위 단계로 나눈다. 모든 작은 단계마다
별도 문서를 만들 필요는 없으며 현재 작업 문서의 체크리스트나 작업 계획으로
관리한다.

## 계획 순서

1. 사용자에게 보이는 가장 작은 전체 흐름을 먼저 고른다.
2. 외부 계약과 안전 조건을 확인한다.
3. 말단 adapter부터 정책·API 방향으로 의존 순서를 정한다.
4. 각 단계에 실행 가능한 검증을 붙인다.
5. 선택 기능과 개선 작업은 필수 흐름 뒤로 보낸다.
6. 실제 측정 전 성능 최적화 작업은 만들지 않는다.

예를 들어 MQTT 전체를 한 번에 추상화하기보다 `설정·메시지 모델 → 연결과
발행·구독 → container 수명주기 → 실제 EMQX 왕복` 순서로 완성한다.

## 작업 착수 기준

다음 항목을 모르면 구현보다 확인 작업을 먼저 한다.

- 변경할 실제 파일과 책임
- 기존 MQTT·HTTP·펌웨어 계약
- 물리 상한과 STOP 조건
- 장치가 없어도 실행할 검증 방법
- 완료 후 호출될 진입점

낮은 위험의 명칭이나 내부 세부 구현은 합리적으로 가정하고 진행할 수 있다.
반면 하드웨어 동작, 공개 계약, 데이터 삭제 또는 구조를 크게 바꾸는 선택은
추정으로 확정하지 않는다.

### 추가 구조를 제안할 때

요청에 직접 포함되지 않았고 현재 기능에 없어도 되는 snapshot·wrapper·base
class·manager·queue·새 dependency는 작업 계획의 확정 항목으로 바로 넣지 않는다.
먼저 현재 문제, 가장 단순한 대안과 추가 구조의 실제 이점을 설명한다. 이점이
안전이나 현재 요구로 명확하지 않으면 사용자 확인 후 계획에 반영한다.

## 테스트 범위

위험에 비례해 검증하고 테스트 개수나 coverage 자체를 목표로 삼지 않는다.

| 변경 | 최소 검증 |
| --- | --- |
| 순수 변환·범위 검증 | 단위 테스트 |
| 상태전이·watchdog·STOP | 시간과 adapter를 가짜로 둔 단위 테스트 |
| MQTT·시리얼·RTSP 경계 | 가짜 경계 테스트와 필요한 실제 통합 테스트 |
| FastAPI route | 요청·응답 계약 테스트 |
| React 변경 | TypeScript build와 주요 사용자 흐름 |
| 펌웨어·릴레이 | 자동 테스트 후 제한된 실물 검증 |
| 문서만 변경 | 링크, 용어, 코드 현황 일치 확인 |

실물 테스트는 자동 테스트를 대체하지 않으며 자동 테스트가 안전 경계를 검증한 뒤
수행한다.

## 완료 기준

다음을 모두 충족해야 작업을 완료로 표시한다.

- 요청한 사용자 흐름이 끝까지 동작한다.
- 실패·취소·종료 경로가 정의되고 검증됐다.
- 관련 자동 테스트와 build가 통과한다.
- 설정 예시와 공개 계약이 코드와 일치한다.
- task 체크리스트와 상태가 현재 구현을 반영한다.
- 관련 없는 임시 코드, 사용하지 않는 추상화와 디버그 출력이 남지 않았다.

선택 개선이나 후속 아이디어가 남아 있다는 이유만으로 현재 작업을 미완료로 두지
않는다. 완료 조건 밖의 내용은 다음 작업으로 명시한다.

## 커밋 단위

커밋은 하나의 논리적 변경을 안전하게 되돌릴 수 있는 단위로 만든다.

- 구현과 그 구현을 검증하는 테스트는 같은 커밋에 포함할 수 있다.
- 해당 변경으로 반드시 달라지는 문서도 같은 커밋에 포함할 수 있다.
- 서로 독립적인 백엔드, React, 인프라 변경은 별도 커밋으로 나눈다.
- 기반 코드, 설계 결정, 장기 작업 목록처럼 검토 목적이 다른 변경은 분리한다.
- 의존성 파일과 그 의존성을 처음 사용하는 코드는 같은 커밋에 둔다.
- 각 커밋은 관련 테스트나 build를 통과해야 한다.

파일 수나 줄 수만으로 커밋을 나누지 않는다. 반대로 하나의 메시지로 설명하기
어려운 두 작업은 같은 커밋에 묶지 않는다. 같은 요청이나 피드백에서 시작됐더라도
서로 독립적으로 설명하거나 되돌릴 수 있는 변경은 별도 커밋으로 나눈다. 커밋 전
staged diff를 확인해 커밋 메시지와 직접 관련 없는 변경이 섞이지 않았는지 검토한다.
커밋 메시지는 변경 결과를 간결한 한국어로 설명한다.

## 범위가 커졌을 때

구현 중 다음 상황이 생기면 계속 확장하기 전에 계획을 갱신한다.

- 공개 MQTT·HTTP 계약이 바뀐다.
- 예상하지 않은 하드웨어 또는 네트워크 제약이 발견된다.
- 한 클래스가 연결·상태·정책을 동시에 소유하게 된다.
- 원래 완료 조건과 무관한 기능이 필요해 보인다.
- 현재 구조로 안전한 종료나 테스트가 불가능하다.

계획 변경은 실패가 아니다. 다만 이미 끝난 범위와 새로 발견된 범위를 구분해
일정과 완료 조건을 다시 명확히 한다.
