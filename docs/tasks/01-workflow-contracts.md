# 01. 상태·워크플로우 계약 확정

## 사용자 결과

얼굴이 보이거나 가려지고, 사용자가 교대하거나 자리를 비우는 모든 주요 상황에서 서버의
현재 사용자와 책상 제어 가능 여부가 모호하지 않게 결정된다. 이후 구현 task는 별도 정책
추측 없이 같은 상태와 API 계약을 사용한다.

이 작업은 설계와 문서 확정만 다룬다. 기능 코드, 모델 선택과 임계값 조정은 후속 task의
범위다.

## 현재 문제

- `CurrentUserSnapshot.status` 초안이 신원(`RECOGNIZED`)과 재실(`VACANT`, `MULTIPLE`)을
  한 축에 섞고 있다.
- 얼굴이 잠깐 보이지 않을 때 사용자 session을 유지할지 종료할지 규칙이 부족하다.
- 얼굴 카메라의 사용자와 자세 카메라의 사람이 같다고 판단할 근거가 정의되지 않았다.
- 오래된 Dashboard가 새 사용자에게 명령을 적용하지 못하게 할 구체적인 요청 계약이 없다.
- 얼굴 등록·재등록·삭제 중 기존 현재 사용자와 자동화를 어떻게 처리할지 불명확하다.
- 현재 사용자가 없을 때 가능한 수동 제어 범위가 확정되지 않았다.

관련 초안은 [사용자 식별과 Vision](../workflow/identity-and-vision.md),
[책상 제어 모드와 높이 프리셋](../workflow/desk-control.md),
[API 계약](../workflow/api-contracts.md)에 있다.

## 확정할 상태 모델

다음 상태를 하나의 enum으로 합치지 않고 각 축의 책임과 freshness를 정의한다.

| 축 | 확정할 내용 |
| --- | --- |
| 신원 관측 | 등록 사용자, 미등록 얼굴, 후보, 불확실과 관측 시각 |
| 재실 | 단일 사용자, 이탈, 다중 사용자, 불확실과 인원수 |
| 자세 | 앉음, 섬, 불확실, 후보 유지 시간과 관측 시각 |
| 사용자 session | 없음, 확정, 재검증, 차단·종료 상태와 `sessionId` |
| 제어 mode | session에 속한 `AUTO`, `MANUAL` 또는 mode 없음 |
| 자동화 | 관측 중, 준비, 이동, 수동, 차단과 차단 이유 |

`CurrentUserSnapshot`에는 최소한 session ID, profile ID, session 상태, 시작·변경 시각과
신뢰 근거를 포함한다. Vision snapshot은 신원·재실·자세와 각 관측 시각을 별도로 제공한다.
동일한 `observedAt` 하나로 서로 다른 카메라의 freshness를 대표하지 않는다.

## 결정 항목

### 사용자 session 연속성

- [ ] 얼굴을 몇 번 연속 확인해야 새 session을 확정하는지 규칙의 형태를 정한다.
- [ ] 얼굴 일시 누락 중 session 표시, Voice 문맥과 AUTO 이동 권한을 각각 정한다.
- [ ] 단일 재실 연속성이 session 유지 근거가 될 수 있는 조건과 최대 재검증 시간을 정한다.
- [ ] `VACANT`, 다른 얼굴, 다중 사용자와 frame 만료 중 어떤 사건이 즉시 STOP 또는 session
  종료를 일으키는지 정한다.
- [ ] A→B 교대 시 A session 종료, 후보 초기화, B 재확정과 AUTO 시작 순서를 정한다.

### 두 카메라 관측 결합

- [ ] 책상 사용 영역 ROI와 카메라별 유효 관측 영역을 정의한다.
- [ ] 두 관측의 허용 시각 차이와 인원수 불일치 처리 규칙을 정한다.
- [ ] 첫 구현에서 사람 Re-ID 없이 단일 책상·단일 사용자 조건으로 fail-closed할 범위를
  명시한다.
- [ ] 자세 관측을 현재 사용자에게 귀속할 수 없으면 새 자동 목표를 금지하도록 정한다.

### 명령과 동시성

- [ ] mode 변경, preset, 직접 목표와 HOLD 중 `expectedSessionId`가 필요한 요청을 정한다.
- [ ] session 불일치는 `409`, 장치 미준비는 `503`, 입력 오류는 `422`처럼 오류 의미를
  통일한다.
- [ ] STOP은 session이나 현재 사용자 유무와 관계없이 항상 접수하도록 명시한다.
- [ ] 현재 사용자 없는 HOLD·직접 목표를 허용할지, 허용한다면 익명 MANUAL 상태를 둘지
  확정한다.
- [ ] profile 설정 CRUD가 현재 사용자·mode·책상 이동을 변경하지 않음을 명시한다.

### 얼굴 등록과 lifecycle

- [ ] 등록·재등록·얼굴 삭제 시작 시 STOP과 자동화 차단 순서를 정한다.
- [ ] 등록 성공 직후 profile을 활성화하지 않고 새 background 식별을 요구한다.
- [ ] 활성 profile 삭제 시 STOP, session 종료와 연관 데이터 삭제 순서를 정한다.
- [ ] 서버 시작 시 저장된 profile이나 과거 session을 현재 사용자로 복원하지 않는다.

## 시나리오 결정표

아래 각 행에 대해 `CurrentUser`, session 유지 여부, mode, 새 자동 목표, 진행 중 이동 STOP과
Dashboard 표시 결과를 기록한다.

- 얼굴이 잠시 가려졌다가 같은 사용자가 다시 보임
- 사용자는 계속 있지만 얼굴 재검증 시간이 만료됨
- A가 이탈한 뒤 B가 들어옴
- A가 있는 동안 B 또는 지나가는 사람이 함께 감지됨
- 얼굴 카메라와 자세 카메라의 인원수가 다름
- 자세 또는 얼굴 frame만 오래됨
- 얼굴 등록 도중 기존 사용자가 자세를 바꾸거나 명령을 보냄
- 이전 Dashboard가 A의 session ID로 B session에 preset을 요청함
- 서버 재시작 직후 카메라 관측이 아직 없음

## 산출물

- 수정된 workflow 문서와 상태 전이표
- 요청·응답 예시를 포함한 API 계약
- 상태 이름, timestamp와 freshness의 공통 용어표
- 자동화 입력 허용 조건과 STOP 결정표
- 후속 task에서 사용할 테스트 시나리오 목록

## 제외 범위

- 얼굴·자세 모델과 라이브러리 선정
- 인식 거리, confidence, 연속 frame 수 같은 실측 임계값 확정
- Pydantic 모델, SQLite migration과 FastAPI route 구현
- Dashboard 화면 디자인과 실제 책상 이동

## 완료 조건

- 모든 시나리오의 현재 사용자, mode, 자동화 허용 여부와 STOP 여부가 하나의 결과로 결정된다.
- 신원·재실·자세·session 상태가 서로 다른 축으로 문서화된다.
- stale Dashboard 명령을 판별하는 공개 필드와 오류 의미가 정해진다.
- 후속 task가 안전 정책을 새로 발명하지 않고 모델과 테스트를 작성할 수 있다.
